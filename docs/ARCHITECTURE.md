# Architecture

> Hosting lifecycle: DigitalOcean was previously validated and intentionally decommissioned for cost control after cloud credits were exhausted. Hosted commands and deployment references below apply to a newly provisioned environment under your control; historical domains are not active service entrypoints.

## 1) Architecture intent

OncoVax is an event-driven cold-storage monitoring platform baseline implemented as a service-based architecture.

The architecture demonstrates an operational engineering baseline for telemetry ingestion, threshold-based alerting, API/UI workflows, persistence, observability, and self-hosted deployment patterns. It is intentionally scoped as an engineering baseline with documented production-hardening gaps.

Scope boundaries for this architecture:

- Telemetry is generated by software simulators in this repository.
- The platform models monitoring, alerting, acknowledgement, and observability workflows rather than physical hardware-fleet lifecycle management.
- The repository does not claim clinical certification, validated regulatory compliance, or complete production hardening.

## 2) Core service architecture

The current architecture is composed of the following services and infrastructure layers:

- **Simulator (`services/simulator/`)**
  - Publishes software-generated telemetry to MQTT topics.
  - Supports configurable device profiles, scenarios, and runtime controls.

- **MQTT broker (Mosquitto)**
  - Provides telemetry and control-topic transport between producers and consumers.

- **Worker (`services/worker/`)**
  - Subscribes to telemetry topics.
  - Validates and normalizes incoming telemetry.
  - Evaluates threshold-based temperature excursions.
  - Persists telemetry and alert-series signals to InfluxDB.
  - Persists mutable operational alert lifecycle records to MongoDB.

- **InfluxDB**
  - Provides time-series persistence for telemetry and alert measurements.
  - Serves as the primary Grafana datasource.

- **MongoDB / Atlas-backed persistence (`MONGO_URI`)**
  - Provides operational persistence for alert lifecycle and acknowledgement records.
  - Stores mutable workflow state rather than an immutable compliance audit log.

- **API service (FastAPI, `services/api/`)**
  - Exposes health and operational endpoints.
  - Serves dashboard assets for operator workflows.
  - Reads and updates operational records in MongoDB.

- **Dashboard/UI (`services/web/`)**
  - Provides an operator-facing interface for summary, alert visibility, filtering, and acknowledgement interactions.

- **Grafana (`grafana/`)**
  - Provides InfluxDB-backed observability dashboards for telemetry and alert signals.

- **nginx ingress (`infra/nginx/nginx.conf`)**
  - Provides the TLS ingress boundary for HTTPS routing, basic-auth protection, and route-level exposure controls when the TLS ingress topology is provisioned.

- **Orchestration adapter (`services/orchestration_adapter/`)**
  - Bridges repository-defined control topics to simulator runtime-control events over MQTT.
  - Is present in local/dev and TLS ingress Compose topologies.

## 3) Data and control paths

### Telemetry ingestion path

1. Simulator publishes telemetry to MQTT.
2. Mosquitto transports telemetry events.
3. Worker subscribes to the configured telemetry topics.
4. Worker validates and normalizes payloads.
5. Worker writes telemetry measurements to InfluxDB.

### Alert generation path

1. Worker evaluates normalized telemetry against temperature-threshold logic.
2. Worker writes alert-series signals to InfluxDB.
3. Worker writes corresponding operational alert lifecycle records to MongoDB.

### Operational API path

1. API reads operational records from MongoDB.
2. API exposes summary, list, detail, filtering, and acknowledgement workflows.
3. Acknowledgement updates mutate the corresponding MongoDB lifecycle record.
4. Dashboard/UI consumes API routes from the same application boundary.

### Observability path

1. Grafana queries InfluxDB for telemetry and alert-series visualization.
2. In the TLS ingress topology, Grafana is reached through protected nginx host routing.

Grafana is an observability surface rather than the authoritative source for MongoDB-backed alert lifecycle and acknowledgement state.

### Runtime-control path

- The orchestration adapter consumes control topics and publishes simulator runtime-control events over MQTT.
- Optional Node-RED flows can provide a local development interface to this control path.
- Runtime control is additive and does not replace the canonical telemetry ingestion path (`MQTT -> worker`).

## 4) Trust and exposure boundaries

### Public-safe route boundary

- nginx exposes `GET /public-health` as a public-safe liveness route without basic auth.
- The route is intentionally narrow and should remain constrained by deployment perimeter controls.
- A successful response establishes route reachability and basic API liveness, not complete internal correctness.

### Protected operational surfaces

- Operational API and dashboard routes are protected by nginx basic auth in the TLS ingress topology.
- Alert acknowledgement route patterns are separately protected and write-rate limited.
- These operational surfaces are not intended to be anonymous public endpoints.

### Grafana boundary

- Grafana is not an anonymous public surface in the TLS ingress topology.
- nginx applies basic-auth protection to Grafana host routing.

### Ingress-layer vs application-layer controls

- Current protection is significantly ingress-layer driven through TLS scaffolding, route segmentation, basic auth, and selected rate limiting.
- Application-layer authentication and authorization are not yet fully implemented as first-class API controls.
- nginx basic auth should therefore not be interpreted as a complete application RBAC implementation.

## 5) Persistence boundaries

### InfluxDB responsibility

- Stores telemetry measurements.
- Stores alert-series measurements for observability and trend analysis.
- Serves as the Grafana time-series query backend.

### MongoDB responsibility

- Stores mutable operational alert lifecycle and acknowledgement records.
- Serves as the API's operational persistence source for summary, list, detail, filtering, and acknowledgement behavior.
- Does not provide an immutable compliance audit-log guarantee.

### Atlas-backed persistence

- The architecture supports MongoDB Atlas-backed operational persistence through `MONGO_URI`.
- This preserves the application's MongoDB persistence contract while allowing storage to be placed in managed infrastructure.
- Atlas compatibility does not by itself establish production-readiness, backup guarantees, or recovery assurance.

## 6) Environment architecture differences

### Local/dev (`infra/docker-compose.dev.yml`)

- Includes the full local stack: simulator, Mosquitto, worker, API/UI, InfluxDB, MongoDB, Grafana, Node-RED, and orchestration adapter.
- Publishes development service ports to the host on loopback only.
- Is intended for local development, integration testing, and end-to-end runtime verification.
- Local direct access does not reproduce the nginx TLS ingress boundary.

### Hosted baseline (`infra/docker-compose.yml`)

- Provides the core self-hosted stack for Mosquitto, worker, API, InfluxDB, and MongoDB.
- Uses environment-file configuration and supports Atlas-backed persistence through `MONGO_URI`.
- Does not add the nginx TLS ingress boundary by itself.
- Any internet-facing use requires operator-managed network perimeter controls and environment-specific security configuration.

### TLS ingress path (`infra/docker-compose.prod.yml` + nginx)

- Adds nginx reverse proxy and TLS certificate mounting.
- Uses protected ingress routing for operational surfaces.
- Exposes the public-safe health path separately from authenticated operational paths.
- Includes simulator, orchestration adapter, and Grafana with configured service restart behavior.
- Requires operator-provided credentials, certificates, DNS, and host-level security controls.

Environment behavior and risk posture differ materially across these deployment modes and must be validated for the target environment.

## 7) Architecture non-claims

This architecture intentionally does not claim:

- integration with a physical medical-device fleet as represented by the repository runtime
- certified clinical or regulated-infrastructure status
- validated regulatory compliance
- complete application-layer authentication or RBAC
- immutable audit logging
- guaranteed recovery or disaster-recovery assurance
- complete production hardening

The current architecture should be treated as a self-hosted engineering baseline with implemented runtime services, deployment patterns, verification paths, and documented operational and security boundaries. Additional hardening and environment-specific validation are required before production use.
